# 生产问题排查与优化手册（NLP / LLM / RAG / Agent）

> 把"生产里真会遇到的问题 + 怎么定位 + 怎么解决"按主题汇总。格式统一：**现象 → 原因 → 解决**。
> 配套代码见 `生产架构/`、`生产_语义检索_纯HF底层/`、`音频制作_双语配音/`、`综合项目/` 等。

## 0. 排查通用套路（先定位，再动手）
- **分层定位**：数据 → 模型 → 检索(RAG) → 生成 → 服务 → 部署。从后往前或从前往后逐层排除，别一上来乱改。
- **最小复现**：把出问题的输入缩到最小、固定随机种子，稳定复现再修。
- **一次只改一处**：改一个变量→看指标→确认因果，别一把梭。
- **看日志和指标**：结构化日志(带 request_id) + p99 延迟/错误率/GPU 利用率，是定位的眼睛。

## 1. 模型：加载 / 输出错误 / 崩溃
| 现象 | 原因 | 解决 |
|------|------|------|
| 模型下载慢/失败 | 网络到 HF 慢、无缓存 | 设镜像 `HF_ENDPOINT=https://hf-mirror.com`；离线预下载到 `HF_HOME` 缓存；容器里打进镜像层 |
| 加载即 OOM | 模型太大/全精度 | 半精度 `torch_dtype=bfloat16`；`device_map="auto"` 分片；量化(4/8bit)；CPU/NVMe offload |
| **输出乱码/明显不准** | **语种不匹配**(英文模型跑中文) | 换对应语种模型：中文情感→`uer/roberta-dianping`、中文检索→`bge-zh`、中文 NER→CLUENER |
| 句向量检索质量差 | **池化方式配错**(mean↔MiniLM，cls↔bge) | 按模型配对池化；mean 必须用 attention_mask 加权(排除 PAD)。见 `生产_语义检索_纯HF底层/pooling.py` |
| 分类/情感总偏一类 | 类别不均衡、阈值不对 | 看 F1/PR 而非 acc；类别权重/重采样；阈值不一定 0.5 |
| 生成幻觉/胡编 | 无检索、无约束、温度高 | RAG 接真知识 + 提示"只据资料答、无据说不知道" + `temperature` 调低 |
| 生成复读机 | 解码参数 | `repetition_penalty=1.2~1.3`、`no_repeat_ngram_size=3` |
| `pipeline("summarization"/"translation"/"question-answering")` 报错 | **transformers v5 删了这些 pipeline** | 用底层 `AutoModelForX + generate` 手写。见 `分章项目/Ch7_进阶_四大NLP任务.py`、本机记忆 env-transformers-v5 |
| 同输入结果每次不同 | 采样/未固定种子 | 评测/复现场景 `do_sample=False` 或固定 `torch.manual_seed` |
| tokenizer/模型不配套报错 | 版本或来源不一致 | `from_pretrained` 同源同版本；requirements 固定版本 |
| 首个请求超慢 | 冷启动加载模型 | **单例 + 懒加载 + 启动预热**(发一条假请求)。见 `model.py` 双检锁 |

## 2. RAG 优化（最常被问，按链路排查）
> 口诀：**检索是上限，生成只是下限**。效果差先查检索，别急着调 prompt。

**召回不准的排查链（顺着查）**
1. **切块质量**：块太大噪声多、太小丢上下文。中文按标点(。！？)切句 + 按字数聚块 + **重叠(overlap)**；一般 200–500 token + 重叠 40–80。中文没有空格，不能按词数切。
2. **嵌入模型是否匹配领域&语言**：中文必须用中文嵌入(bge-zh)；专业领域考虑领域微调。E5/bge 记得加 query/passage **前缀指令**。
3. **是否该上混合检索**：向量对"精确术语/编号/型号"不敏感 → 加 **BM25 关键词** 双路召回 → **RRF 融合**。见 `Agent进阶案例/案例3_混合检索RAG_LangGraph.py`。
4. **是否该重排**：向量是双塔(快但粗) → 粗召回 top-50 → **cross-encoder 精排** top-5(准)。见 `生产_语义检索_纯HF底层/rerank.py`。
5. **query 改写**：口语问题改成检索友好表达；可用 LLM 扩展同义 query。
6. **top-k 与相似度阈值**：召回太少漏、太多噪声；低于阈值走兜底。

| 现象 | 原因 | 解决 |
|------|------|------|
| 换个说法就搜不到 | 关键词字面匹配 | 语义向量检索；再叠混合检索兜精确匹配 |
| 答案幻觉/瞎编 | 检索到的没用上/无约束 | 提示强制"据给定资料答、标引用编号、无据说不知道"；答案做**有据校验**；召回空走兜底 |
| 上下文太长、token 贵、被截断 | 把整篇文档塞进去 | 只回 **top-k 精简片段 + 来源**，让 LLM 基于片段答 |
| 无法溯源 | 没带来源 | 检索结果带 doc_id/出处；生成要求输出引用编号供前端高亮 |
| 知识过时 | 想靠微调塞知识 | **知识用 RAG**(改库即更新)，微调只管"怎么答"。知识会变，微调追不上 |
| 检索慢/内存爆 | 全量在内存精确检索 | 上向量库(Qdrant/Milvus) + ANN 索引(HNSW/IVF)；见 `生产架构/生产02` |
| 效果没法量化 | 没评测集 | 建离线集，统计 **召回率/命中率/幻觉率 + LLM-as-judge**。见 `生产工程补齐/补4` |

## 3. 推理 / 部署性能
| 现象 | 原因 | 解决 |
|------|------|------|
| 首 Token 延迟(TTFT)高 | 预填充慢/无 KV 复用 | KV Cache、prefix caching(相同前缀复用)、投机解码；简单请求路由到小模型 |
| 吞吐低、GPU 空转 | 逐条推理 | **连续批处理**(vLLM/TGI)、动态批。见 `综合项目/项目6`(真跑批处理对比) |
| 推理 OOM | 模型大/batch 大/序列长 | 量化(AWQ/GPTQ/GGUF)、张量并行、offload、限 `max_length`/`batch_size` |
| 高并发雪崩 | 无限流无排队 | 限流 + 队列 + 超时 + 熔断；无状态服务 + K8s 多副本 + HPA 按 GPU 利用率扩缩 |
| 相同请求重复算 | 无缓存 | prompt/embedding/结果缓存(Redis)。见 `音频制作_双语配音/cache.py` 内容哈希缓存 |
| 每请求都加载模型 | 没单例 | 启动时/首次加载一次常驻，依赖注入复用 |
| 冷启动慢 | 容器起来才加载 | 预热 + 保活副本 + 就绪探针(未热不接流量) |
| llama.cpp/GGUF 想 CPU 跑大模型 | 未量化 | GGUF Q4_K_M；`llama_cpp.server` OpenAI 兼容。见 `生产工程补齐/补6` |

## 4. 训练 / 微调
| 现象 | 原因 | 解决 |
|------|------|------|
| loss 不降 | 学习率不对/数据脏/标签错 | 调 lr + warmup；抽查数据/标签；先小数据过拟合验证管道通 |
| 过拟合(验证回升) | 数据少/模型大/训太久 | 早停、weight_decay、dropout、加数据/增强、降复杂度 |
| 训练 OOM | 显存不够 | 梯度累积 → 梯度检查点 → 混合精度(bf16) → LoRA → QLoRA → DeepSpeed ZeRO + offload |
| LoRA 没效果 | target_modules/r/alpha/数据 | 给 q/v(或 all-linear)、r=8~32、alpha≈2r；数据量/质量够 |
| SFT 学不到"怎么答" | 在 [PAD]/prompt 上算了 loss | [PAD] label 设 **-100**；prompt masking 只对 Response 段回传 loss |
| 微调后通用能力退化 | 灾难遗忘 | 小学习率、LoRA(不动基座)、混入通用数据 |
| 训完不知道好不好 | 没评估 | 留验证集 + compute_metrics；生成任务加人工/judge |
| GRPO 训不动/崩 | 组内无方差 / KL 爆 | 挑"有对有错"的题(全对全错优势=0)；监控 reward↑/reward_std 别塌 0/KL 别爆。见 `Ch12` |

## 5. Embedding / 检索服务（呼应 `生产_语义检索_纯HF底层/`）
| 现象 | 原因 | 解决 |
|------|------|------|
| 向量质量差 | 池化配错/未用 mask | mean 要 mask 加权、bge 用 cls；见 `pooling.py` |
| 余弦分数不对 | 没 L2 归一化 | 归一化后点积=余弦；`normalize=true` |
| 索引报维度错 | 换了模型维度变了 | 换模型要重建索引；缓存键含模型名 |
| 批量编码 OOM | batch/max_len 太大 | 调小 `EMB_BATCH_SIZE`/`EMB_MAX_SEQ_LEN` |
| 并发写索引出错 | 竞态 | 加锁 + 落盘(见 `index.py`)；规模大换向量库 |

## 6. TTS / 音视频服务（呼应 `音频制作_双语配音/`）
| 现象 | 原因 | 解决 |
|------|------|------|
| 中英混排读音错 | 一个音色读全部 | **按脚本分段**：中文段中文音色、英文段英文音色，再拼接。见 `tts.py` |
| 英文音标不准 | 生僻词走规则近似 | `pip install eng-to-ipa` 自动切全量准确；前端标注"近似" |
| ffmpeg 报错/拼接失败 | 各段规格不一致/滤镜转义 | **统一采样率/声道/位深**再 concat；drawbox 表达式注意逗号转义。见 `video.py` |
| 视频里中文/音标变豆腐块 | 字体缺字形 | 用含中文+IPA 字形的字体(Arial Unicode)。见 `system.resolve_font` |
| 导出视频慢/阻塞 | 同步生成 | **异步 job + 轮询进度** + 内容缓存 + 并发限制。见 `jobs.py` |
| mlx 高音质下不动 | 模型/网络 | 自动**回退 say**(零下载)，服务不中断。见 `tts._synth_chunk` |

## 7. Agent / 工具 / MCP
| 现象 | 原因 | 解决 |
|------|------|------|
| Agent 死循环烧 token | 无步数/超时上限 | 设 `max_steps` + 每步超时 + 兜底收尾。见 `生产工程补齐/补3` 手写 ReAct |
| **提示注入**(工具返回内容当指令执行) | 输出可信 | 工具输出隔离/不可执行、参数校验、最小权限、human-in-the-loop、审计 |
| 工具选错/不调 | description 差 | 工具 name/description/参数写清(LLM 靠它选)；生产用 function calling 比文本解析稳 |
| 上下文被工具结果撑爆 | 结果不裁剪 | 只回 top-k 精简 + 来源，长结果摘要后再喂 |
| 某工具挂拖垮整链 | 无熔断 | 超时 + 熔断 + 降级(该工具不可用时跳过/兜底) |
| 小模型选路由不稳 | 让弱模型做编排 | 用**确定性状态机**编排(LangGraph)，节点内才用 LLM。见 `Agent进阶案例` |
| 多服务器工具重名 | 命名冲突 | 命名空间限定 `nlp.get_sentiment`/`retrieval.search` |

## 8. 服务工程 / 上线 / 兜底
| 主题 | 做法 |
|------|------|
| **统一异常** | 自定义异常 + 全局处理器；区分 4xx(用户错)/5xx(系统错)；不泄露栈。见 `core/exceptions.py` |
| **监控告警** | p99 延迟、QPS、错误率、GPU 利用率、队列长度 → 阈值告警 |
| **降级兜底** | 模型异常→规则兜底；向量库超时→切关键词检索；低置信度→转人工 |
| **灰度 A/B** | 按 user_id 哈希稳定分流一部分到新版本，配评测对比再全量。见 `生产工程补齐/补5` |
| **限流/超时/重试** | 网关限流；客户端超时 + 指数退避重试(幂等操作) |
| **配置管理** | 环境变量/多环境；密钥用 Secret 管理，不写死 |
| **Prompt/模型版本化** | Prompt 存版本、可回滚、可追溯；模型存仓库(HF Hub/MLflow/S3) + 版本号 |
| **训推分离** | 训练产出→模型仓库→推理服务拉取；别一个进程又训又服务 |

## 速查：一句话急救
- **模型输出不准** → 先问"语种/池化/是否该 RAG"，再调 prompt。
- **RAG 差** → 查检索链(切块→嵌入→混合→重排→改写)，别只调 prompt。
- **慢** → TTFT 靠 KV Cache、吞吐靠连续批处理、OOM 靠量化。
- **崩** → 限流+超时+熔断+降级兜底+多副本。
- **忘了在哪** → 打开对应文件顶部 docstring；面试点见 `面试大纲/`。

## 10. 回答不满意 / 不正确 → 系统调优 playbook（最高频实操）
> 核心心法：**先定位是哪一层错，再按"便宜→贵"的顺序调**。别一上来就微调/换模型(最贵最慢)。

### 第一步：定位是哪一层错（把中间结果打出来看）
一个坏答案，先看它错在哪一环——**把中间产物打印出来**，逐段验证：
1. **理解层**：模型有没有理解意图？(把改写后的 query / 意图分类结果打出来)
2. **检索层(RAG)**：检索到的资料对不对？(把 top-k 片段 + 分数打出来) —— 资料就没找对，后面白搭。
3. **生成层**：资料对，但答歪/漏/编？(把喂给模型的完整 prompt + 模型原始输出打出来)
4. **能力层**：是不是模型本身能力不够？(换个更强模型试同一条，能对→是模型问题)

> 一句话判断：**检索到的对不对** 决定是"RAG 问题"还是"生成/prompt 问题"。

### 第二步：按黄金顺序调（从 0 成本到高成本）
| 顺序 | 手段 | 什么时候用 | 具体怎么做 |
|:--:|------|-----------|-----------|
| 1️⃣ | **改 Prompt**(最快 0 成本) | 几乎所有问题先试这个 | 指令更明确/角色设定；**加约束**("只据资料答、无据说不知道")；**加 few-shot 示例**(给 2~3 个理想问答对)；**加 CoT**("先一步步分析再给结论")；**结构化输出**(要 JSON 就给 schema) |
| 2️⃣ | **调检索(RAG)** | 定位到"资料没找对" | 切块/嵌入选型/混合检索/重排/query 改写/top-k(见本手册第 2 节) |
| 3️⃣ | **调解码参数** | 答不稳定/太发散/太长 | `temperature` 调低(更稳)、`top_p`、`max_tokens`、`stop` 词 |
| 4️⃣ | **加后处理 / 护栏** | 格式/可信度问题 | 输出**格式校验 + 不合格自动重试**；**有据校验**(答案是否被资料支持)；**self-consistency**(采样多次投票取多数)；**critique-revise**(让模型自我批判再改一版)；规则过滤敏感/越界 |
| 5️⃣ | **检索式 few-shot** | 任务多样、固定示例不够 | 从示例库里**动态挑与当前输入最相似**的几个当 few-shot |
| 6️⃣ | **微调(SFT/LoRA)** | 前面都不够、要固定格式/领域风格/新能力 | 收集**高质量修正样本**(把坏例子改成理想答案)做 SFT；见 `Ch11`。注意：**新知识用 RAG 不用微调** |
| 7️⃣ | **换 / 升级模型** | 定位到"模型能力不足" | 换更强/更大/领域专用模型；或简单任务路由到小模型省钱 |

### 第三步：症状 → 直接调法（对照表）
| 症状 | 最可能原因 | 优先调法 |
|------|-----------|---------|
| 答非所问、没听懂 | query 理解偏 | query 改写、意图分类、few-shot |
| 要 JSON 却给散文/格式乱 | 约束不够 | 强约束 + few-shot 示范 + 结构化输出 + 校验重试 |
| 漏了关键信息 | 召回不足 或 没要求覆盖 | 提高 top-k/改切块/重排；prompt 明确"覆盖以下要点" |
| **编造 / 幻觉** | 无据可依/温度高 | RAG 接真资料 + "无据说不知道" + 温度调低 + **有据校验 + 无据兜底** |
| 太啰嗦 / 太简短 | 没定长度 | 明确长度要求、`max_tokens`、few-shot 示范长度 |
| **不听指令 / 忽略约束** | 指令弱/模型弱 | 关键约束**前置并重复**、结构化输出、换更强模型 |
| 中英文混乱 | 语言没约束/模型语种不对 | 明确"用中文回答"、换对应语种模型 |
| 前后矛盾 / 每次不一样 | 采样随机 | 降 `temperature`、**self-consistency 投票**、评测时固定 seed |
| 动不动就拒答/过度保守 | 系统提示太紧/阈值高 | 放宽系统提示、调低置信度阈值、few-shot 示范"可以答" |
| 事实过时 | 知识写死在模型里 | RAG 接最新知识库 |

### 第四步：评估驱动闭环（★别凭感觉调，否则"修好 A 坏了 B"）
1. **建 bad-case 回归集**：每发现一个坏答案，就把 (输入, 期望, 当时输出) 收进测试集。
2. **每次调完跑回归**：用固定测试集 + 指标(准确率/召回率/幻觉率) + **LLM-as-judge** 打分，确认整体变好、没退化。见 `生产工程补齐/补4`。
3. **灰度上线**：新 prompt/模型按流量 A/B，线上指标不降再全量。见 `生产工程补齐/补5`(Prompt 版本管理)。
4. **线上持续收集**：埋点采集低分/被踩的回答，回流成新的 bad-case，形成"发现→归因→调→回归→灰度"的闭环。

> 记忆：**Prompt → 检索 → 参数 → 护栏 → few-shot → 微调 → 换模型**，从左到右越来越贵，永远从左边先试；每一步都用**回归集**验证，而不是拍脑袋。
